# Lazy-stream KV cleanup ownership refresh

## Decision

**No open PR directly implements candidate `4053b1c3`. One active draft needs
coordination before a contribution can be proposed.**

The candidate remains a substantive residual fix for a remote-prefill request
that passes the early serving call and then fails admission when its lazy result
iterator is first consumed. The current evidence supports delayed producer-lease
release until connector cleanup. It does not prove a permanent leak. It also
does not make the preflight capacity problem in #58192 a KV-capacity leak.

Open draft PR #59343 changes the same
`GenerateBaseServing._with_kv_transfer_rejection_cleanup` method. Its change
tracks engine admission with a context variable. Its focused tests consume
`AsyncLLM.generate()` while the outer cleanup wrapper is still active. Its file
diff does not add guards to the lazy Chat, Completion, or Responses iterators
after their `create_*` methods return. Candidate `4053b1c3` instead passes one
request-local guard into those endpoint methods and catches only
`QueueOverflowError` and `MaxQueuedTokensError` during initial iterator
consumption. This is a material implementation and behavior difference. It is
not safe to claim that #59343 owns the same fix. It is also not safe to ignore
the overlap: both patches edit the same base wrapper, so a human contribution
must explain the residual lazy path and coordinate or rebase if #59343 moves.

## Named ownership threads

### #50425

Issue #50425 remains open. It has no newer comment after 2026-07-31. The last
comment says the originally reported v0.18.0 Mooncake cancellation problem
appears fixed indirectly by merged PR #41269. That conclusion is about cleanup
before engine admission in the tested create-time cancellation path. It does
not include a queue rejection raised when a lazy endpoint iterator is first
advanced.

Two open PRs still mention #50425:

- #50565, head `d84bcca15fc0c4543ca419bd0742a0a8f38da8d3`, prevents stale
  Mooncake receive completion after early abort.
- #57529, head `1a37b8d4d29373287e65dbda8c72e965ea45aa72`, adds a Mooncake
  failure ledger.

Both heads equal the prior closed evidence. Neither changes the candidate's
four serving modules. Neither is a direct duplicate.

### #42442

PR #42442 remains open at head
`4fbb6652db12098887ae7223c760dbb2650cd575`. It adds `abort()` when a
`ValueError` or `VLLMValidationError` propagates after `add_request()` created a
queue. It changes only `vllm/v1/engine/async_llm.py` and its focused test. This
is post-registration engine cleanup. Candidate `4053b1c3` handles two queue
admission errors before engine registration. The ownership and files differ.

### #58192

Issue #58192 remains open. Its latest comments point to #58477 and #58478.
Both PRs are closed. They reserved `max_num_queued_reqs` capacity at preflight
so requests could be rejected before expensive rendering. They changed
`AsyncLLM` admission accounting and its tests. They did not change the four
candidate serving modules and did not add remote-prefill rejection cleanup.

This is an adjacent capacity-admission design. It is not evidence that a lazy
queue rejection sends the connector notice. The candidate report must not call
the #58192 preflight behavior a KV-capacity leak.

## Contribution ownership conclusion

The duplicate check does not require rejecting candidate `4053b1c3` as already
implemented. A human contribution must still do all of the following:

1. Coordinate with #50425 because that issue owns the reported cleanup area and
   its last comment says current main fixed the known create-time case.
2. Explain that the residual case occurs after a lazy endpoint returns but
   before the request is registered with the engine.
3. Mention draft #59343 as an exact same-method overlap and explain why its
   wrapper-scoped admission test does not exercise the endpoint iterator path.
4. Rebase and reassess the guard design if #59343 changes or merges.
5. Keep the effect statement limited to earlier producer-lease release. The
   retained source evidence gives a configured default cleanup interval of 30
   seconds. It does not prove permanent resource retention.
